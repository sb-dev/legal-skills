## 1. Scope and questions

Seven tool categories that `legal-skills` might orchestrate instead of rebuilding: (1) document comparison / redlining, (2) document parsing and clause extraction, (3) authority and citation verification, (4) open-source licence scanning and SBOM, (5) privacy / data mapping, (6) policy / compliance-as-code, (7) secret and PII detection for the Stage 10 routing step.

Questions asked of each tool:

- Can it run on the user's machine with nothing leaving it (Stage 10 route L; class 1, 2, 6 material)?
- What is its licence, and does the licence allow a permissively licensed skills project to call it or copy from it?
- Is it maintained (last commit, release, archive flag)?
- What does it emit that an agent can consume (CLI, library, MCP, file format)?
- Where does it fail?

Method limits. GitHub facts come from `gh api` on 2026-09-19 (licence = GitHub's SPDX detection unless a LICENSE file was read; "stars" rounded; "open issues" is GitHub's count and includes pull requests). Commercial products were **not inspected at their own pages**; they appear at headline level only and every statement about them is marked weak. Accuracy figures are the projects' own claims unless I ran the tool. Two tools were run locally on public, synthetic input (L-T1, L-T2); nothing confidential was sent anywhere, no sign-ups, no keys.

## 4. Overlap with `legal-skills`, and what is missing

**Near-equivalents seen from this assignment** (the skills landscape is another assignment's subject; these surfaced here):

- **Anthropic `knowledge-work-plugins/legal`** (L-57; Apache-2.0; ~25k stars on the parent repo): skills named review-contract, triage-nda, compliance-check, legal-risk-assessment, vendor-check, brief, legal-response. Bodies were not read here. This is the closest direct overlap in form and is permissively licensed.
- **Anthropic `docx` skill** (L-09): already gives Claude a tracked-changes editing method, under a no-copy licence. `legal-skills` should depend on "a docx capability if the host has one" and otherwise call Python-Redlines.
- **Python-Redlines as a GitHub Action** (L-01): "redline every .docx changed in a pull request" already exists. Do not rebuild it.
- **ORT evaluator / cdx-audit** (L-32, L-37): licence policy automation exists. `legal-skills` adds the legal reading of the findings, not another scanner.
- **legislation.gov.uk MCP server** (L-28): an execution layer for UK legislation V1 / V2 / V4 exists, from the data owner's GitHub org.

**Genuinely missing**

1. **A maintained UK / EU citation extractor.** Nothing open and maintained parses neutral citations, law-report citations (`[1932] AC 562`), OSCOLA forms or ECLI from prose. eyecite returned nothing for them (L-T1); Blackstone is dead; TNA's patterns live inside a Lambda service. `neutral_url` validates one string at a time. The guardrail says do not build a citator; a small regex extraction step inside a verification skill is not a citator, but the boundary needs a decision.
2. **A free UK later-treatment source** (V5). Still none.
3. **Any tool for V2 / V3** (does the pinpointed text say this; does it support the proposition). The 2026 benchmark (L-29) shows even strong agents are poor at it. This is the project's own work, not something to orchestrate.
4. **A local, open redline tool that applies a reviewer's proposed edits as tracked changes** into an existing .docx while keeping formatting. Python-Redlines compares two finished files; the permissive options stop there. Workable route: write the edited copy, then compare original against edited with Python-Redlines.
5. **Legal-meaning sensitivity detection.** No tool detects privileged, NDA-bound or special-category *content*; Presidio finds identifiers, scanners find keys. Stage 10 classification stays a human-and-model judgement.
6. **Machine-readable UK / EU legal obligations.** None found; consistent with the guardrail against building a policy-as-code engine.

## 6. Failure modes and limits observed

- **Silent loss of tracked changes and comments**: pandoc's default when reading .docx is `accept` (L-08). A reviewer would never see the counterparty's deletions or margin comments.
- **Empty result read as "clean"**: eyecite on UK text returns nothing (L-T1); Presidio and Gitleaks returning nothing proves little. Every detector needs the rule "no findings ≠ none present".
- **404 read as "fabricated"**: Find Case Law and CourtListener are incomplete; older UK authorities have no neutral citation (L-T2, L-22). A miss means "not verified here".
- **200 read as "verified"**: existence (V1) only. The benchmark in L-29 shows the hard errors are pinpoints, misquotes and misdescribed holdings.
- **Declared ≠ actual licence**: Syft, cdxgen, pip-licenses, license-checker and Trivy's standard mode report package metadata. Only file scanners (ScanCode, Trivy `--license-full`) look at the text, and they produce noisy partial matches.
- **Tool labels mistaken for legal conclusions**: Trivy's "forbidden / restricted / reciprocal" are Google's internal categories (L-38). Whether copyleft is triggered depends on linking, distribution and the deployment model, which no scanner knows.
- **Version drift in redline output**: Python-Redlines 1.0.0 changed algorithm; the same inputs give a different redline than 0.x (L-01). Pin and record the version in the work product.
- **Bus-factor risk**: Python-Redlines / Docxodus depend on essentially one maintainer (L-01, L-02). Keep the text-diff fallback.
- **Abandonment is common in legal NLP**: LexNLP (2023), Blackstone (2021), CUAD code (2021), scrubadub (2023), OpenDSR (2020), askalono (archived), diff-match-patch (archived), original license-checker (2019), and **Fides archived in 2026**. Any dependency needs a re-check date.
